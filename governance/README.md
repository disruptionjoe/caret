# Governance

How the project is run and how contributions are reviewed.

## Review Process

Contributions are reviewed by maintainers. The criteria:

1. Does it add practical utility?
2. Is it clear and precise?
3. Does it follow the existing voice and structure?
4. Does it avoid duplicating concepts that already have terms?

## Decision Making

Design decisions are made by maintainers and documented transparently. If a decision affects how people use the notation, it gets written down with rationale.

## What counts as canonical

Two things can be canonical: notation and vocabulary.

**Notation changes** go through `notation/DECISIONS.md`. Any change to the spec requires a documented decision with rationale. The notation folder is the source of truth — if anything else in the repo conflicts, the notation wins.

**Vocabulary changes** go through the field guide glossary lifecycle:

- **Emerging** → Pattern observed but not yet validated across ecosystems
- **Fragmented** → Multiple terms exist for the same concept; no winner yet
- **Canon** → Community has converged on meaning; term is stable

## How governance relates to CONTRIBUTING.md

CONTRIBUTING.md defines what's welcome and the quality bar. This file defines how submitted contributions get reviewed and how decisions get made. CONTRIBUTING is the front door; governance is the back office.
